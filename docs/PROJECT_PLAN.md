# Web 與 API 多引擎動態安全檢測暨結果整合後端系統

版本：規劃稿 1.0｜日期：2026-10-15｜狀態：未實作、未量測

## 1. 專題摘要（可改寫放入提案）

本專題針對需要檢查 Web 應用與 REST API、但缺乏專職資安人力的小型開發團隊，設計一套以後端服務為核心的多引擎動態安全檢測系統。系統以授權範圍為前提，整合 ZAP 與 Nuclei 執行不同面向的動態檢測，並保留 Schemathesis 作為 API 規格導向測試的擴充引擎。透過非同步任務管理、隔離執行環境、統一發現格式、保守去重、證據追溯及複掃比較，將原本分散的工具輸出轉為可供開發者檢視與追蹤的議題。研究將以受控靶場及固定測試案例，比較單一工具與整合流程的已知弱點檢出情形、重複資訊負擔、執行可靠性及人工整理時間。系統不保證發現所有漏洞，不將一般 API 規格違反直接視為資安漏洞，也不取代人工滲透測試。

## 2. 問題定義：不要把「整合工具」當成使用者需求

### 2.1 目標使用者（待訪談驗證）

主要使用者設定為有 Web/API 上線前檢查需求的小型產品團隊、校內專題團隊及負責測試的後端工程師。部署場景以自管的測試環境、隔離 staging 副本與教學靶場為主，不以公開任意 URL 掃描服務為目標。

### 2.2 待驗證的痛點假設

| 假設 | 對應設計 | 要如何驗證，而非只靠宣稱 |
|---|---|---|
| 多工具各自設定認證、範圍及輸出，導入步驟分散 | 統一 target、auth profile、scan profile | 記錄完成相同任務所需步驟、時間及錯誤 |
| 開發者難以判斷多份告警是否重複 | 統一 Observation/Finding 與保守關聯 | 人工標記重複配對，量測誤合併與漏合併 |
| 掃描失敗與零告警容易混淆 | 完整任務/引擎狀態及覆蓋資訊 | 測試 timeout、憑證失效、Parser 錯誤 |
| 修補後缺少可比較的紀錄 | 版本、scope、auth、policy 快照與複掃差異 | 使用已知修補/未修補的 fixture 驗證 |
| 掃描過程可能越界或洩漏測試 Token | 出站約束、授權、秘密遮罩 | 檢查封鎖靶場的實際收包數與資料洩漏 |

上述是研究假設，不是已完成的市場調查。建議訪談 3–5 位有實際開發/測試經驗的人，詢問最近一次掃描流程、整理報告時間、認證設定困難與最常忽略的資訊；不要只問「你會不會想用」。

### 2.3 核心價值主張

**我們不取代既有掃描器，而是讓開發者能在同一個受控流程中，啟動互補檢測、辨識執行缺口、追溯證據，並比較修補前後的結果。**

相對單獨使用 ZAP/Nuclei，可能增加的價值是工作流程的一致性和結果可比較性；是否增加弱點檢出或減少工時，必須由實驗確認。不能僅因工具數量增加，就宣稱準確率更高。

## 3. 題目定位與三個研究問題

建議題目：**Web 與 API 多引擎動態安全檢測暨結果整合後端系統之設計與實作**。

這是「系統設計 + 可重現實驗」型畢業專題，不必硬包裝成新的漏洞偵測演算法。若提供 Token 與 OpenAPI，屬於具規格/認證資訊的動態測試；不是因此就變成原始碼白箱分析。

| 研究問題 | 比較方式 | 主要衡量 |
|---|---|---|
| RQ1：相同總掃描預算下，多引擎是否增加可確認的安全發現？ | ZAP、Nuclei、ZAP+Nuclei；有第三引擎時再追加 | 已知案例 recall、precision、獨有 TP、耗時與請求數 |
| RQ2：統一格式與去重是否降低人工整理負擔？ | 同一組輸出：未合併列表 vs 保守去重後列表 | 去重 precision/recall、誤合併、人工整理時間 |
| RQ3：系統是否能正確處理越界、失敗與複掃的不確定性？ | 注入故障及已知修補狀態 | 越界實際收包數、取消/清理、錯誤狀態與誤判修復次數 |

## 4. 掃描工具選型

### 4.1 採用兩個核心、第三個有條件加入

| 引擎 | 專題角色 | 結果來源 | 階段 |
|---|---|---|---|
| ZAP | Web 爬取、被動/主動檢查、OpenAPI 導向 API 掃描 | 固定版本 JSON 報告與必要流量/進度資訊 | P0 必做 |
| Nuclei | 人工審查的 HTTP 模板，用於已知問題、暴露資訊與錯誤設定檢查 | JSONL findings、執行 metadata、流量紀錄 | P0 必做 |
| Schemathesis | 依 OpenAPI 產生 API 邊界/負向輸入與規格檢查 | 鎖定版本 JSON/NDJSON；必要時 JUnit/HAR | P1 第三引擎 |

ZAP 的 Automation Framework 可用於工作編排，API 掃描會依輸入規格匯入端點；Web profile 與 API profile 不應混為同一套設定。[S02–S05]

Nuclei 使用模板執行檢查，提供 JSONL、速率與模板控制；本專題只使用受限 HTTP 模板，而不是把所有可用模板與協定全部打開。[S06]

Schemathesis 是規格/性質導向的動態 API 測試工具，不是單純的傳統漏洞掃描器。可提供 JSON/NDJSON 等報告；格式以實際鎖定版本為準。[S07–S09]

### 4.2 不要誇大第三引擎的安全意義

某輸入造成 HTTP 500，可以是健壯性問題；回應不符 schema，可以是契約問題。只有存在相應安全影響與證據時，才適合人工歸類為資安發現。預設保留 `security / contract / robustness / informational`，分別計數。

BOLA、權限越界與業務流程問題涉及「哪個身分可存取哪個物件」，不能只靠 API 規格與一次回應就保證全面判斷。[S14] 多身分權限測試可列後續研究，不列第一版已覆蓋能力。

### 4.3 本版不再加第四套工具

不加入另一個大型 DAST、單一 SQL 注入工具或主機弱掃套件來湊數。第三引擎的加入條件是前兩個已完成真實端到端掃描、解析、取消、錯誤處理與報告；否則將時間用在可靠性和實驗。

## 5. 功能範圍與明確排除

### 5.1 P0：第一版必須完成

| 模組 | 最小可交付內容 | 驗收重點 |
|---|---|---|
| 平台存取 | 管理員/專案操作/唯讀 API key | 無公開註冊；跨專案不可讀寫 |
| 目標與授權 | Target + ScopeGrant、期限與允許 origin/path/method | 核准前不能掃；範圍變更需新快照 |
| API 規格 | 上傳 OpenAPI 3.0 JSON/安全 YAML，固定目標 origin | 僅同文件 $ref；不抓外部 URL |
| 目標認證 | 靜態 Bearer、API key header、既有 Cookie | 加密、只寫不讀、protected preflight |
| 任務管理 | 建立、排隊、查詢、取消、超時、故障追蹤 | 不因 API 重啟丟失狀態 |
| 隔離 Runner | 固定 Docker 映像、流量/資源/時間限制 | 無 Docker socket 暴露給 API/掃描器 |
| ZAP Adapter | Web 與 API 兩個受控 profile | 真實輸出可解析、零告警不等於失敗 |
| Nuclei Adapter | 審查模板白名單與 JSONL Parser | 不執行任意模板；保存版本資訊 |
| 結果處理 | Observation、Finding、保守去重 | 不刪來源、不錯把同 CWE 都合併 |
| 報告與複掃 | JSON/Markdown、triage、可比性判定 | 未再觀察到不自動等於已修補 |
| 安全與稽核 | 遮罩、scope、權限、審批/操作紀錄 | secrets 不進一般 log/報告 |
| 實驗 | 可切換修補版本的靶場與測試資料 | 單工具與整合工具用相同總預算 |

### 5.2 P1：進度允許再做

Schemathesis Adapter、OpenAPI 3.1 相容性、API operation 覆蓋率精細化、一次 CI pipeline 呼叫範例。以 JSON/Markdown 報告為主；排版式報告和 dashboard 不加入必要範圍。

### 5.3 本版不做

自訂前端、AI 自動判讀/RAG、原始碼 SAST、容器/主機 CVE 掃描、GraphQL 完整支援、WebSocket、SOAP、檔案上傳流程掃描、OAuth/SSO/MFA 自動登入、手機 App、全網資產盤點、任意 shell/模板執行、外部 OAST、自動修補、正式站台與商用多租戶。

第三方靶場本身可能附帶頁面，不代表本專題需開發前端。REST API 與內建 API 文件足以展示後端。

## 6. 使用者流程

操作人員先由管理員取得有專案權限的 API key，建立 target 與申請 scope。管理員核對自有/授權環境、限定允許範圍與期限。操作人員上傳已去識別化的 API 規格、必要的測試認證資料，選擇 profile 後提交 scan。系統回傳 scan_id，Runner 在重新確認 scope 和認證後執行工具。完成後，使用者查閱統一 findings 與各引擎狀態、標註誤報或確認問題，再於修補後建立新的 scan 做差異比較。

重要：保留舊 scan；複掃是新的一次執行，不覆蓋舊證據，不重用舊任務狀態。

## 7. 後端技術與架構決策

| 層次 | 建議選擇 | 原因與取捨 |
|---|---|---|
| API | Python 3.12 + FastAPI + Pydantic 2 | 以有型別的 REST 契約實作，不做 UI |
| 持久化 | PostgreSQL + SQLAlchemy 2 + Alembic | 保存任務、結果、權限、快照與 migration |
| 非同步工作 | Celery + Redis | 長工作與 API 程序分離；DB 仍為狀態依據 |
| 啟動與隔離 | Docker；獨立 Runner VM | 各掃描器環境分離，避免依賴衝突與高權限暴露 |
| 出站控制 | 既有 HTTP proxy 的規則模組 + 防火牆 | 不能只依賴掃描器自己守 scope |
| 報告 | JSON + Markdown | 易於 API/CI 消費，不做前端頁面 |
| 測試 | pytest + fixture/contract/e2e/security 測試 | Mock 與 live 分開，不混淆完成度 |
| 依賴固定 | uv.lock、映像 digest、模板 commit/hash | 追溯實驗與 Parser 版本 |

FastAPI 官方對較重、可獨立程序的工作提到 Celery 等佇列工具；掃描不應放在 API request 或單純 BackgroundTasks 內等待。[S10] Celery 的工作仍需考慮重新派送與冪等，不能視為 exactly-once 執行器。[S11]

架構採「模組化單體控制平面 + 一個隔離 Runner」，不把每個模組拆成獨立微服務。第一版所有引擎依序執行，共用單 target 的掃描預算，降低競爭與故障排查成本。

詳細資料模型與狀態見 `ARCHITECTURE.md`；路由契約見 `API_CONTRACT.md`。

## 8. 專題要自己實作什麼

你們不必重寫 SQL 注入或 XSS 的掃描邏輯；應自己實作的是：授權/範圍模型、任務生命週期、Adapter 與 Parser、共用流量預算、憑證注入、Observation/Finding 模型、去重規則、可比性判定及實驗流程。這些部分必須有測試和設計理由，才能與單純寫三行 CLI 的包裝區別。

不將「AI 寫了程式」列為功能成果；Claude Code 只是開發工具。未來 AI 摘要可用去識別化證據作為輸入，仍須保留引用和人工判斷，但本版不以此為核心。

## 9. 可靠性、可重現性與限制

每次 scan 保存 target/scope/spec/auth role 的版本、工具映像 digest、ZAP add-on 版本、Nuclei 模板 hash、profile、程式 commit、測試 seed、靶場快照、請求數和完成原因。隨機工具、目標狀態與網路仍會造成差異；版本固定是提升可追溯性，不是保證每次 byte-for-byte 相同。

沒有 OpenAPI 時只做可發現的 Web/端點檢查，不宣稱 API 規格覆蓋完整。認證失效時標記 auth coverage 不完整；前端瀏覽器深度流程、複雜登入與業務邏輯問題列為限制。

## 10. 16 週工作計畫（假設 3 人）

| 階段 | 週次 | 交付 | 放行條件 |
|---|---|---|---|
| M0 可行性與範圍凍結 | 1 | 兩工具隔離靶場 smoke test、版本紀錄、研究問題 | 取得真實輸出樣本；不可只看到程序啟動 |
| M1 API/資料基礎 | 2–3 | FastAPI、DB、key、target、scope、secret、outbox、FakeRunner | 不啟動真工具也可完成任務流程與權限測試 |
| M2 Runner 與安全邊界 | 4–5 | 隔離網路、egress guard、資源限制、取消/timeout/reconcile | 越界實際收包為零、取消無孤兒容器 |
| M3 ZAP 真整合 | 6–7 | Web/API profile、auth preflight、JSON Parser | 已知靶場正常/異常、失敗及取消均可辨識 |
| M4 Nuclei 與結果整合 | 8–9 | 模板白名單、JSONL Parser、Observation/Finding、去重 | 兩引擎完成同一端到端流程且不誤合併 |
| M5 報告與複掃 | 10–11 | triage、JSON/Markdown、版本比較、API demo | 不可比/認證失效不會被宣稱修補成功 |
| M6 選配或補強 | 12–13 | Schemathesis 或補齊可靠性、覆蓋、文件 | P0 未過關則不加第三引擎 |
| M7 實驗與口試 | 14–16 | 重複實驗、分析、論文/報告、展示腳本 | 原始結果可追溯、可重建一輪示範 |

三人分工：A 負責 API/DB/權限；B 負責 Runner/網路/工具；C 負責正規化/去重/測試/報告。安全邊界、去重規則與實驗標記需至少兩人交叉審閱，不能完全各做各的。

若只有 1–2 人或 8–10 週，保留兩工具、單 Runner、單專案部署、靜態認證、JSON/Markdown 報告與小型受控資料集；拿掉第三引擎與 CI 整合。不能用刪除授權、隔離和故障處理換取工具數量。

## 11. 初始資源配置與部署假設

先用既有 Linux VM/伺服器，規劃總資源約 8 vCPU、16 GB RAM、50–80 GB 可用磁碟；控制平面與 Runner 分成兩個 VM 或等效隔離環境。這是開發起點，並非最低官方需求或性能保證，需依 M0 壓測調整。若只有 8 GB，減少靶場數量、限制 ZAP heap，持續採串行測試。

不需要 GPU，也不需要 LLM API 或向量資料庫。先不購買雲端服務；開源工具的實際授權及再散布要求需在 M0 記錄，不應將「可下載」視為所有用途都無限制。[S02–S09]

證據設建議留存上限：加密原始資料 7 日、遮罩報告 30 日，可依校內要求調整。磁碟容量、敏感資料與保留期間須寫入運維文件，不無限堆積 HAR/response body。

## 12. 主要風險與降階策略

| 風險 | 早期徵兆 | 應對 |
|---|---|---|
| 工具 proxy/auth 設定不一致 | 工具直接連外或登入前後結果相同 | M0/M2 流量驗證；不受控的 profile 不放行 |
| API 程式完成但掃描仍不可靠 | 只有 Mock、沒有真實 Parser fixtures | M3/M4 各設 live DoD，不延到期末 |
| 去重錯誤隱藏漏洞 | 相同 CWE 被合併成一筆 | 用保守語意映射、保留 observation、測誤合併 |
| 三工具全開拖垮靶場 | 5xx/延遲/記憶體上升 | 共用預算、串行、健康監測、狀態化停止 |
| 第三工具結果不像資安漏洞 | 大量 schema/500 告警 | 分類並分開評估，不灌水 security 數量 |
| scope 太複雜而做不完 | 雙週結束仍無拒絕越界測試 | 先只支援隔離 HTTP 靶場；HTTPS profile 通過 CA/guard 測試後才開 |
| 報告過度承諾 | 零告警被寫成「安全」 | 強制顯示範圍、失敗、未測項目與不確定性 |
| 實驗只為自己的規則量身打造 | 加一個 fixture 就寫一個模板 | 保留 holdout、凍結模板、區分自訂規則實驗 |

## 13. 驗收標準

所有以下數值均是**驗收目標**，不是現有成績。

功能方面，兩工具必須可從 API 建立掃描到取得真實 findings，並能展示 auth 掃描、取消、超時、工具壞掉、Parser 壞掉、部分結果及複掃比較。

安全方面，預定測試集合中的越界流量不得抵達禁止目標；跨專案讀取必須被阻止；已知秘密不得出現在普通回應/log/報告；失敗的網路 guard 不得默認放行。測試集合通過不代表全世界所有繞過都已防住。

品質方面，scope/狀態機/去重/遮罩模組以 branch coverage ≥80% 為門檻，並要求設計好的安全負向測試全數通過。受控重複執行以 ≥95% 正常完成率作為觀察目標；若未達成，也應如實分析而非改寫數據。

研究方面，需呈現單工具和整合版本的 TP/FP/FN、請求量、耗時、去重錯誤及至少一次已知修補情境。不得預先承諾高於單一工具的百分比。

## 14. 最終交付與展示

交付完整後端原始碼、依賴鎖檔、Docker/網路設定、DB migration、API 規格、操作文件、授權靶場環境、測試集、已去識別化輸出、實驗結果與畢業專題報告。原始密鑰、Token、個資與未遮罩第三方證據不交付到公開 Git。

展示以 API client 呼叫：建立 target/scope → 提交兩引擎 scan → 查狀態 → 查 findings 與 evidence → 展示同問題多來源 → 切換已修補靶場 → 複掃比較 → 展示越界拒絕與取消。現場不必等待全量掃描；可使用已保存且註明時間/版本的真實結果，再即時執行小型受控案例。

建議報告章節為緒論、需求分析、相關工具與文獻、系統設計、系統實作、安全與測試、實驗分析、結論與限制。每個「改善」都對應到實驗表格或測試證據。
